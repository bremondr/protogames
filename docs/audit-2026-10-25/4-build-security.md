## 2. New findings

### N4-1 (Low) Pull requests on the old layout get no preview and the bot comments a 404 link
Location: `scripts/build-site.js:150-155` (`exportApp` throws "does not contain app/index.html"), `.github/workflows/pages.yml` comment step (unconditional).
What happens: since the landing/app split, any open same-repo PR whose head still has the root `index.html` layout is skipped by the build (a console warning in the CI log only). The PR still receives "Preview: …/preview/pr-N/", which 404s, and nothing explains why. Today only #100 is open (it has a live preview), so no current victim; it will hit any long-lived branch.
Repro: `re4/repo`, previews.json with `refs/previews/pr-1` = `origin/experimental`, pr-2 = `origin/docs-bug-audit`; output "Skipping pr-1: refs/previews/pr-1 does not contain app/index.html", `_site/preview/` has no pr-1/pr-2.
Fix: make the build write a built/skipped summary (JSON) and have the comment step say "No preview: rebase on main" when skipped (same fix as L27).

### N4-2 (Low) The landing page of a preview does not refresh its project list when another tab saves
Location: `landing.js` end of file (`storage` listener), `scripts/preview-runtime.js`.
What happens: `landing.js` re-renders only when `event.key` starts with `ProjectLibrary.KEY_PREFIX` (`protogames_project:`). In a preview the real key in the event is `preview:pr-N:protogames_project:<id>` (the runtime prefixes below the app's view, but `StorageEvent.key` carries the raw key), so the check never matches. Production works.
Repro (`re4/t6.js`): landing in one tab, open `app/?showcase=peg-solitaire` in a second tab, wait 1 s. Production list gained "Triangle peg solitaire" without reload; the preview list (`/preview/pr-6/`) stayed the same.
Fix: in `landing.js` also accept keys that end with the prefix after the preview prefix (`window.PG_BUILD && event.key === PG_BUILD.storagePrefix + ...`), or simply re-render on any storage event.

### N4-3 (Low) A newer autosave of a still-open old-version tab is deleted by the legacy import
Location: `app/js/projectLibrary.js` `importLegacy` (the `store.removeItem(key)` after the `if`; lines ~158-175).
What happens: the project id is derived from the old key (`recovered-<tab id>`) and is created only when it does not exist yet, but the old key is removed unconditionally. If an old-version tab is still open and keeps autosaving `protogames_autosave:<tab>`, the next `importLegacy()` (landing page load, or any app start, which both call it) drops that newer data and keeps the first, older copy.
Repro (`re4/t12.js`, on the landing page): write a legacy autosave with 5 tiles, `importLegacy()`, write the same key again with 50 tiles, `importLegacy()` again: legacy key gone, `recovered-abc123` still 5 tiles.
Impact: transitional, only while upgrading with old tabs open; data loss of last edits. Fix: when the project already exists, overwrite it if the legacy payload is newer (compare `timestamp`) before removing.

### N4-4 (Low) Saved data on the old github.io origin is not reachable after the domain move, and the docs say it is
Location: `docs/DEPLOYMENT.md` "The landing page" section ("Saved data ... is stored per browser origin, not per path, so it is still there after the move").
What happens: the statement holds for the move from `/` to `/app/` but not for #104: `https://bremondr.github.io/protogames/…` now answers `301 → https://protogames.eu/…` (checked with `curl -I`, e.g. `/preview/pr-100/app/` → `https://protogames.eu/preview/pr-100/app/`), and localStorage is per origin, so projects saved on the old address never reappear. Share links survive (path and hash are kept), local projects do not. The Pages API shows `cname: protogames.eu`, so the old origin can no longer be visited to export.
Fix: add a note to DEPLOYMENT.md/README (people who used the old address must have exported projects before 2026-10-19), nothing more can be done in code now.

### N4-5 (Info) Landing CSP carries an unneeded `data:` image source; app CSP has a redundant host
Location: `index.html:7` (`img-src 'self' data:`), `app/index.html:10` (`connect-src … https://queue.simpleanalyticscdn.com https://*.simpleanalyticscdn.com`).
Evidence: the landing page contains no `data:` URL anywhere (grep `data:` hits only the CSP line), its images are the same-origin logo and inline SVG. `style-src 'unsafe-inline'` is needed there (one `<style>`, six `style=` attributes). In the app the wildcard host already covers `queue.`. Landing CSP otherwise tight: `default-src 'self'; script-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'self'; form-action 'none'`; no CSP violation logged on load (`t1.js`). Harmless; drop `data:` to match "least privilege". Landing has no analytics script (visits to `/` are not counted, only `/app/`), which may or may not be intended.

### N4-6 (Info) Preview isolation does not cover indexed access
Location: `scripts/preview-runtime.js:35-52`.
Evidence (`t5.js` in a preview): `localStorage.length` is 0 (prefix applied) while `Object.keys(localStorage).length` returns 8 and lists production's `protogames_project:*` keys. The app never uses it (grep: no `Object.keys(localStorage)`, `localStorage[`), so no current bug; same trust note as F5. A test that greps `app/` for these patterns would keep it so.

### N4-7 (Info) Deferred scripts: the page is visible and inert until the scripts have run
Location: `app/index.html:664-708` (46 `defer` scripts), no loading state or `noscript`.
Evidence (`t4.js`, server delaying every `.js` by 2.5 s, screenshot `re4/defer-1.5s.png`): at 1.5 s the whole toolbar is shown with enabled buttons (Export, Share, Load), the board-shape picker and palette selects are empty, `Main`/`UI` undefined, canvas not initialised. No console errors; order is preserved, the three `DOMContentLoaded` handlers (countryBoard, countryRegions, main) still run in the old order after all deferred scripts. On the real site (HTTP/2) this window is short (the PR measured 0.9 s) so it is cosmetic. Also: on `file://` the app loads and starts fine under the CSP (`t7.js`).

### N4-8 (Info) Share-link visitors pay for a full landing page before being forwarded
Location: `index.html:13-14`, `landing.js:7-11`.
Evidence (`t3.js`, `t8.js`): `/#b=…` makes two navigations; before the forward the browser loads the landing HTML (47 KB), logo and `projectLibrary.js` (120 KB uncompressed in total). The forward only happens after the deferred script runs, so the landing page may flash first. Could be a small non-deferred `<script src="landing.js">` placed first in `<head>` (external, so CSP-safe) that forwards before the body is parsed. Cosmetic.
